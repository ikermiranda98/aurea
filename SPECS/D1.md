# D1 — Conexión TWS (client ids, persistencia, heartbeat, reconexión)

## 1. Propósito

Portar el cliente de socket TWS de Openbot (`@stoqey/ib` parcheado) a `crates/tws`: conexión TCP al API de TWS (7497 paper / 7496 live), client ids 1000–9999 persistidos por instalación, detección del código **326** (id ocupado), reconexión cada 5 s con watchdog de 15 s, y persistencia de la cuenta activa. Es la base de D2-D4.

## 2. Comportamiento exacto observado en el código TS

### 2.1 Parámetros de conexión

- Host/puerto del motor: `options.host ?? "127.0.0.1"`, `options.port ?? 7497` (`trading.ts:781-782`).
- `PUERTOS_IBKR = [{port:7497, live:false}, {port:7496, live:true}]` (`:462-465`); `entornoPuerto` (`:469-473`) sólo nombra "· live"/"· paper" en esos dos.
- `conexionIb({host, port, reconnectInterval: 5_000, connectionWatchdogInterval: 15}, alOcupado)` (`:941`, `:4009` para MT5 no aplica).
- `CONEXION_FIRME_MS = 1_500` (`:746`): TWS acepta el socket y medio segundo después envía el 326 y corta; el enlace sólo cuenta como establecido si sobrevive a esa ventana (`asociarCuentas`, `:1263-1268`).

### 2.2 Client ids

- `CLIENT_ID = 30` (`:742`) es el fallback extremo de migración.
- Resolución del id del motor (`resolverClienteMotor`, `:789-815`): build → `TRADING_CLIENT_ID` (entero 1000-9999, si no log-warning) → `trading_meta.client_id` (si no válido, regenera) → genera `1000 + floor(random()*9000)` y lo persiste (upsert) → si la DB falla, `catchCause` → 30.
- Enlaces registrados: `siguienteClienteEnlace = 71` (`:921`), incremental por enlace (`:1398-1399`), "lejos de los CLIENT_ID de los bots".
- `clientIdEnUso(host,port,clientId)` (`:598-616`): abre un `IBApiNext`, conecta con ese id, vigila `errorSubject` por `code === 326` o `/already in use/i`, timeout 2,5 s → `false` (libre). Se usa en el sweep (`:2149`) y antes de arrancar un bot (`:2241`).

### 2.3 El parche de `@stoqey/ib` (`patches/@stoqey%2Fib@1.6.13.patch`)

El patch corrige **dos** sitios idénticos (`api-next.js`): al procesar un `position` con tamaño cero, el código hacía `accountPositions.splice(changePositionIndex)` (borra **todos** los elementos desde ese índice) en vez de `splice(changePositionIndex, 1)` (borra **uno**):

```
-                        accountPositions.splice(changePositionIndex);
+                        accountPositions.splice(changePositionIndex, 1);
```
(2 ocurrencias: `@@ -263,7` y `@@ -361,7`.)

Implicación para el cliente Rust: al aplicar una actualización de posición con `pos == 0`, eliminar **exactamente una** entrada del índice; no es un detalle cosmético (un bug que borraba la cola de posiciones del login).

### 2.3b Handshake real verificado en `@stoqey/ib@1.6.13` (paquete npm)

El socket v100+ abre en **dos pasos**, no con el formato antiguo `API\0<versión>\0<id>\0`:

1. **Cabecera cruda** (`Socket.onConnect`): `API\0` + `u32` big-endian con la longitud de la cadena +
   `"v100..193"` (sin NUL final). `193` es `MAX_SUPPORTED_SERVER_VERSION`
   (`CME_TAGGING_FIELDS_IN_OPEN_ORDER`); `100` es `MIN_VERSION_V100`.
2. El servidor responde con su frame de versión: `["<serverVersion>", "<hora de conexión>"]`
   (el fixture usa `["193","20261105 03:55:06 CET"]`), **sin** id de mensaje.
3. El cliente envía **`START_API`** ya con framing normal: `["71","2","<clientId>",""]`
   (`START_API=71`, versión 2, id, capacidades opcionales vacías).

Consecuencias: el client id **no** viaja en la cabecera; el 326 real llega **después** del `START_API`
(el fake de los tests puede enviarlo antes, y el cliente ya lo detecta). El cliente D1 implementa
este flujo y emite `IbEvent::ServerVersion { version, time }` antes de `Connected`.

### 2.4 Aviso 326 (`registro-ib.ts`, 30 líneas)

- `CLIENTE_OCUPADO = 326`; `OCUPADO = new RegExp("Code: 326\\b")`.
- La librería emite el 326 **solo por el logger** (nivel INFO), nunca por `errorSubject`. `conexionIb` inyecta un `logger` cuyos `debug/warn/error` son no-ops y cuyo `info` llama `alOcupado()` si algún arg casa con `OCUPADO`; `ib.logLevel = LogLevel.INFO`.
- `clienteOcupado(enlace)` (`trading.ts:956-966`): `ocupado = Date.now()`; log `trading.log.ibkr.client_id_in_use` (distinto para el primario y para un enlace) con `client`/`link`; se emite como mucho una vez por minuto (el debounce de `pushLog`, `:1107-1115`).

### 2.5 Máquina de estados de la conexión (`asociarCuentas`, `:1252-1299`)

- `connectionState` Connected → `conectado = true`; **esperar 1,5 s**; si sigue conectado, limpiar `ocupado` y log `connected_primary`/`connected_link` con `host:port` + `entornoPuerto`.
- Disconnected → `conectado = false`; si es el primario, `positions.value = []` y `positionKey = ""`; borra `posicionesIbkr`/`preciosIbkr` de sus cuentas; si `desconexion.pedida` → log `disconnected_by_user` y limpiar el flag; si `ocupado !== null` → no logúa pérdida (el rechazo ya explicó); si no → `lost_primary`/`lost_link` con "retrying every 5 s".
- `disconnect` del usuario (`:1788-1794`): `desconexion.pedida = enlacePrimaria.conectado; ib.disconnect()`; devuelve null.
- `connect` (`:1780-1786`): `abrirTws()` (abre TWS si está cerrado, `:1754-1771`), limpia `desconexion.pedida`, y si ya está conectado devuelve la cuenta; si no, `ponerEnMarcha` (`:1776-1779`): log + `ib.connect(clienteMotor)`.
- `accountSelect` sobre un enlace IBKR no conectado llama `ib.connect(enlaceActiva.cliente)` (`:3928-3929`); `IBApiNext.connect` sólo actúa si está Disconnected.

### 2.6 Persistencia

- `trading_meta.client_id` (arriba). `trading_meta.cuenta_activa` (`:1049`), `carpeta-sistemas` (`:3767`), `bucle-motor` (`:2747`), `bot-token:<id>` (`:1594`), `bots-mt5-instrumentos` (`:1515`).
- `trading_link` por cada enlace (`:1405-1409`, `:4015-4019`); `trading_account` por cuenta (`sincronizarCuentas`, `:2697-2731`).

### 2.7 Arranque

- `bootClaim` (`:3784-3812`) del lease; `enlacePrimaria` se crea en el layer (`:1421-1424`) pero **no conecta**; el primer `tick` con lease llama `ponerEnMarcha` (`:2791-2794`). Nada abre TWS al arrancar.
- `enlazar` persiste y conecta; `linkAdd` con la dirección del panel no persiste y connecta el primario.

## 3. Edge cases y condiciones de error

- **326**: el socket se acepta y se cae a los ~0,5 s; sin el logger parcheado leería "conecta y se cae sin motivo". El motor debe distinguir "id ocupado" de "pérdida de conexión" y **no** reintentar en bucle silencioso.
- **Id inválido en env/persistencia** → warning y regeneración; nunca un id fuera de 1000-9999.
- **DB caída al resolver el id** → 30 (fallback extremo) y la app sigue.
- **`connect` repetido** → idempotente (devuelve la cuenta; no duplica el socket).
- **`disconnect` sin conexión** → `desconexion.pedida = false`; devuelve null.
- **TWS no acepta (502 ECONNREFUSED)** → el aviso se reformula a "TWS is not accepting connections… retrying every 5 s" (`:1689-1694`); debounce 60 s.
- **Reconexión después de caída** → el primario vacía posiciones y reconecta a los 5 s; el usuario debe pulsar Connect tras un `disconnect` deliberado.
- **Dos motores en un TWS** → cada uno con su `client_id` persistido; si colocan, el 326 lo nombra.

## 4. Mapeo TS→Rust

- **Socket**: TWS API es TCP con mensajes longitud-prefijada (big-endian u32 + campos NUL-terminados), **no** WebSocket. `crates/tws` con `tokio::net::TcpStream` + codec propio (encoder/decoder de campos) o crate `ibapi` si se valida. El test-oráculo `trama()` (`trading-engine.test.ts:38-43`) define el framing exacto.
- **Cliente**: `crates/tws/src/client.rs` con estado `ConnectionState{Disconnected, Connected}`, `reconnect_interval = 5s`, `connection_watchdog_interval = 15s`; tarea de reconexión en `tokio::spawn`.
- **326**: el decoder debe reconocer el mensaje de error con `reqId = -1`, code 326, y emitir un evento `ClientIdInUse`; el log interno del cliente seroutea a un callback (equivalente del logger parcheado).
- **Id del cliente**: resolver en `crates/trading` (A5) y pasarlo al `connect(client_id)`; persistir en `trading_meta`.
- **`@stoqey/ib` patch**: en Rust, al aplicar `position` con tamaño 0, `remove(indice)` (un único elemento); test de regresión con dos posiciones.
- **Streams**: `connectionState` → `tokio::sync::watch::Sender<ConnectionState>`; `errorSubject` → `mpsc::UnboundedSender<IbError>`; `accountSummary`/`accountUpdates`/`positions`/`openOrders`/`pnl` → callbacks o `mpsc` consumidos por `crates/trading`.
- **`desconexion.pedida`** → `AtomicBool` en el handle del motor.

# C2 — Egress WARP (ruteo del tráfico LLM, rotación por rechazo)

## 1. Propósito

Portar `ghost-egress.ts` (235 LOC) y adaptarlo a la arquitectura de Aurea: el tráfico LLM **no** sale del proceso del engine, sino del sidecar `opencode serve` que hospeda el harness. Por tanto el egress natural en Aurea es el **modo proxy de `warp-cli` + `HTTPS_PROXY`** para el sidecar, no el pin de `hosts` con un `fetch` envuelto. Este spec fija el comportamiento observado en Openbot y su traducción a Aurea.

## 2. Comportamiento exacto observado en el código TS

### 2.1 Estructura de `ghost-egress.ts`

- `GATEWAY = "opencode.ai"` (`:21`); `TRACE_PATH = "/cdn-cgi/trace"`; `PROBE_TIMEOUT_MS = 8_000`; `MAX_REDIRECTS = 5`.
- `POOL = { keepAlive: true, maxSockets: 32, maxFreeSockets: 8 }` (`:30`): el keep-alive es lo que hace significativa la rotación (los sockets sobreviven a la petición; al rotar se descarta el pool entero).
- `isGateway(url)` (`:44-48`): `https:` y puerto 443 (o vacío) y `host === "opencode.ai"` o `host.endsWith(".opencode.ai")`.
- Estado a nivel de módulo: `target: string | undefined` y `pool = new Agent(POOL)` (`:156-157`); `rebind()` destruye el pool y crea uno nuevo (`:159-162`).
- `wrap(base)` (`:167-214`): devuelve un `fetch`; si `target` está definido y la URL es el gateway, abre la petición al **address literal** (`host: address`, `port 443`, `servername: target.hostname`, `headers.host = target.hostname`) siguiendo hasta 5 redirecciones dentro del gateway; si la redirección sale del gateway, pasa al `base`. Cualquier otra URL usa `base` sin tocar.
- `point(addresses)` (`:215-227`): deduplica los candidatos con `:` (IPv6), y por cada uno: fija `target`, `rebind()`, y sondea con `probe()`; el primero que responde `{address, exit}` gana; si ninguno, `target = undefined` + `rebind()` y `None`.
- `probe(address, agent)` (`:96-135`): `GET https://<address>/cdn-cgi/trace` con `servername: opencode.ai`, `host: opencode.ai`; exige `statusCode 200`, `ip` presente, `warp === "on"` y `req.socket.remoteFamily === "IPv6"`; si no, error (no es un aterrizaje).
- `release()` (`:228-231`): `target = undefined` + `rebind()`.

### 2.2 Uso desde `ghost.ts`

- `rotate` llama `egress.point([...resueltaAAAA, ...PIN_LITERALS])` (`:720`) tras ganar el `/64`; si `egress` no está montado, el veredicto es sólo por traza (`:715-718`).
- `release` llama `egress.release()` **antes** del `warp-cli disconnect` (`:813`), para que el gateway vuelva a la ruta de la máquina y ninguna petición quede apuntando a la dirección que se va a quitar.
- El pin de `hosts` sigue existiendo como higiene de la máquina (lo lee el resolver del desktop), pero **ya no es lo que hace funcionar la rotación** (`:728-730`).

### 2.3 UI/trigger del anillo

- `packages/app/src/usage/free-daily-ring.tsx`: `sellar(origin)` (`:455-509`) llama `experimental.ghost.rotate({origin})`; `soltar()` (`:161-175`) llama `experimental.ghost.release()`; `refresh()` (`:181-…`) llama `experimental.ghost.status()`; `origin` puede ser `"manual" | "auto" | "limit"` (`packages/schema/src/ghost.ts:17`).
- Los retries del harness se surfacen como `session.status{retry}` (lo documenta el plan, §4.1).

## 3. Traducción a Aurea: proxy de `warp-cli` + `HTTPS_PROXY`

En Aurea el traffic LLM sale del sidecar `opencode serve` (el harness de Zeron habla HTTP+SSE con `opencode serve`). El mecanismo equivalente, sin pin de `hosts` ni `fetch` envuelto en el engine, es:

1. **Modo proxy**: `warp-cli --accept-tos mode proxy` (WARP actúa como proxy local; el puerto por defecto es `127.0.0.1:40000`, consultable con `warp-cli proxy port`). En este modo **no** hace falta escribir `hosts` ni elevar: el proxy enruta por el túnel.
2. **Variables de entorno del sidecar**: al arrancar `opencode serve`, el engine le pasa `HTTPS_PROXY` (y `HTTP_PROXY`/`ALL_PROXY` según el cliente HTTP que use el sidecar; el esquema es `socks5://127.0.0.1:<puerto>` si WARP expone SOCKS5, o `http://127.0.0.1:<puerto>` si expone HTTP) y `NO_PROXY=127.0.0.1,localhost,::1` para que el tráfico local (IPC del engine, MCP) no salga por el proxy. **El esquema exacto y el puerto deben validarse en la fase 4** (ver `warp-cli mode proxy` / `warp-cli proxy port` en la máquina real); el mecanismo (variables de entorno del sidecar) es el que se especifica.
3. **Rotación**: tras ganar un `/64` nuevo, se hace `warp-cli disconnect`/`connect` (o `registration new` si no hay IP). En modo proxy, el proxy local sigue escuchando; el **siguiente** request del sidecar sale por el túnel nuevo. No hay que reiniciar el sidecar ni reescribir `hosts`; el pool de conexiones del sidecar debe descartarse (si el cliente HTTP del sidecar mantiene keep-alive, conviene que la rotación coincida con un reinicio del sidecar o que el proxy cierre las conexiones).
4. **Verificación de aterrizaje**: el probe de Openbot (`curl` a `cloudflare.com/cdn-cgi/trace` con `ip=` y `warp=on`, y `remoteFamily IPv6`) se mantiene como comprobación de que la salida es la nueva; en Aurea se hace **desde el engine** (no desde el sidecar), igual que `ghost.ts`.
5. **Release**: al renovarse el día UTC (C1), `egress.release` → quitar `HTTPS_PROXY` del sidecar (reiniciarlo con el entorno limpio) **antes** de `warp-cli disconnect`, para que ninguna petición quede apuntando al túnel que se cae.
6. **Rechazo del gateway**: los frames `session.status{retry}` del harness (plan §4.1) indican reintento; el anillo de Aurea debe rotar por `origin:"limit"` cuando el gateway rechace (429/límite free), con el mismo trigger que `free-daily-ring.tsx` (`:455-509`).

## 4. Edge cases y condiciones de error

- **Sin egress montado**: `rotate` responde sólo por traza (`ok:true` si `curl` a `opencode.ai` sale limpio) y no promete nada sobre la ruta de la app.
- **Candidato que no demuestra IPv6 dentro de WARP**: se descarta; `point` deja el egress **limpio** y `rotate` es `ok:false`.
- **Redirección fuera del gateway** → pasa al canal normal (un login o docs no deben ir por el egress).
- **Demasiadas redirecciones** → error.
- **Pool con keep-alive**: si no se descarta al rotar, las peticiones siguientes pueden seguir saliendo por el `/64` viejo; por eso `rebind()` destruye el pool.
- **Hosts no escribible**: en Openbot el pin es opcional para la rotación (el egress es lo que la hace funcionar); en Aurea con proxy mode ni siquiera aplica.
- **WARP sin modo proxy** (sólo `mode warp`): el sidecar no puede usar `HTTPS_PROXY`; en ese caso el egress degrada al pin de `hosts` (C1) y a la comprobación por traza.
- **Servicio WARP parado**: `net start` en el preflight; el proxy no levanta.

## 5. Mapeo TS→Rust

- **`crates/warp/egress.rs`**: en Aurea no envuelve un `fetch`; gestiona el **entorno del sidecar**. API:
  - `async fn point(candidates: &[String]) -> Option<Exit>` (valida cada candidate con un probe HTTPS por address literal y `servername`, requiriendo `ip`/`warp=on`/familia IPv6 — el probe sí es portable 1:1 con `reqwest`/`hyper`);
  - `async fn release()`;
  - `proxy_env() -> Vec<(String,String)>` con `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY`;
  - `apply_to_sidecar()`: reinicia (o reconfigura) el sidecar con el entorno; el harness de Zeron ya gestiona el sidecar (`crates/harness/src/opencode/`), así que el módulo expone el env y el harness lo aplica.
- **Sidecar**: al arrancar `opencode serve`, pasar el env del proxy; al rotar, si el cliente HTTP mantiene pool, reiniciar el sidecar (el harness ya tiene ciclo de vida).
- **Probe**: `curl -6 -s --max-time 8 https://cloudflare.com/cdn-cgi/trace` (o `reqwest` con `resolve` a la IPv6 y `danger_accept_invalid_certs` no; se verifica `warp=on` y la familia).
- **Día UTC / release**: `crates/warp` (C1) llama a `egress.release` antes del `disconnect`.

## 6. Test-oráculo

- No hay tests de `ghost-egress.ts` en Openbot; el estándar es el criterio de Lane C2: **rechazo simulado → rotación; tráfico del sidecar sale por el proxy**.
- Tests a escribir en `crates/warp`:
  - probe: un servidor HTTPS local con certificado de prueba que responde `ip=…`/`warp=on` y se verifica la familia IPv6; candidatos que fallan no dejan egress apuntado;
  - `proxy_env` produce las variables correctas con `NO_PROXY` de loopback;
  - integración: sidecar fake que lee `HTTPS_PROXY` y se comprueba que su tráfico sale por el proxy (servidor SOCKS5/HTTP local que cuenta conexiones);
  - release: tras `release`, el sidecar se reinicia sin proxy.

## 7. Criterio de aceptación

> **C2** Egress: modo proxy de WARP + `HTTPS_PROXY` para el sidecar `opencode serve`; detección de rechazo vía retries del harness (los frames `session.status{retry}` ya se surfacen). *Criterio: rechazo simulado → rotación; tráfico del sidecar sale por el proxy.*
